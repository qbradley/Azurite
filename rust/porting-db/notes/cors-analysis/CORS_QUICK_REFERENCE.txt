KEY DIFFERENCES IN LOGIC
─────────────────────────

1. CORS Middleware Instance Count:
   TypeScript: 2 independent instances registered (both run always)
   Rust: 2 instances, but second only runs if first doesn't error (line 234)

2. OPTIONS Method Handling:
   TypeScript: 
     - corsRequestMiddleware skips OPTIONS (line 153-154)
     - optionsHandlerMiddleware processes OPTIONS (line 37)
   
   Rust:
     - corsErrorRequestMiddleware skips OPTIONS (line 231)
     - corsRequestMiddleware skips OPTIONS (line 231)
     - optionsHandlerMiddleware skips non-OPTIONS (line 117)
     - But runs AFTER serialization

3. Error Propagation:
   TypeScript:
     - Each middleware calls next(err) or next()
     - Express continues pipeline regardless
     - Error can be intercepted at any point
   
   Rust:
     - Middleware returns Option<BoxedMiddlewareError>
     - Caller (blob_request_listener_factory) decides whether to continue
     - Conditional logic at line 234 can break the chain

4. CORS Header Writing:
   TypeScript:
     - Sets headers before next() call
     - Always in memory before serialization
   
   Rust:
     - Sets headers on GeneratedHttpResponse
     - But if serializer already ran, might be ignored

WILDCARD ORIGIN MATCHING
─────────────────────────

Both implementations match `*.contoso.com` against `foo.contoso.com`:

TypeScript approach:
  1. glob-to-regexp library: `*.contoso.com` → regex
  2. Case-insensitive test()
  3. Simple and reliable

Rust approach:
  1. regex::escape() to escape special chars
  2. Replace escaped wildcards: `\*` → `.*`
  3. regex::RegexBuilder with case_insensitive
  4. Functionally equivalent, manual but correct

EXAMPLE: How an OPTIONS Preflight Should Work
────────────────────────────────────────────────

Client sends:
  OPTIONS /container HTTP/1.1
  Host: devstoreaccount1.blob.core.windows.net
  Origin: http://example.com
  Access-Control-Request-Method: PUT
  Access-Control-Request-Headers: Content-Type

Server logic flow:
  1. Receive OPTIONS request
  2. Extract Origin, Access-Control-Request-Method, Access-Control-Request-Headers
  3. Load service properties (CORS rules)
  4. For each CORS rule in order:
     - Check if Origin matches allowedOrigins (exact or wildcard)
     - Check if requested method matches allowedMethods
     - Check if requested headers match allowedHeaders
     - If all match: ACCEPT and return response
  5. If no rule matches: REJECT with 403

On success (match found):
  HTTP/1.1 200 OK
  Access-Control-Allow-Origin: http://example.com
  Access-Control-Allow-Methods: PUT
  Access-Control-Allow-Headers: Content-Type
  Access-Control-Max-Age: 3600
  Access-Control-Allow-Credentials: true

On failure (no match):
  HTTP/1.1 403 Forbidden
  Content-Type: application/xml
  <?xml version="1.0"?>
  <Error>
    <Code>CorsPreflightFailure</Code>
    <Message>CORS not enabled or no matching rule found for this request.</Message>
  </Error>
