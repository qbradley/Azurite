CONTROL FLOW HIGHLIGHTS
-----------------------
OperationQueue:
  • Lazy callback enqueue → semaphore acquire → execute → event notify next

MemoryExtentStore:
  • Stream→Buffer accumulation → size-check insert → metadata update
  • multistream composition for range reads

FSExtentStore:
  • Pool selection → file open/reuse → streamPipe + fdatasync → metadata update
  • Error: truncate → mark idle
  • Active extent tracking via linear search

LokiExtentMetadataStore:
  • init: stat file → load/create → collection ensure → save
  • updateExtent: find by id → upsert or insert
  • listExtents: build filters → query → pagination marker extraction

AllExtentsAsyncIterator:
  • Constructor: snapshot time
  • next(): call listExtents with batch size 1000 → check nextMarker → set done

ZeroBytesStream:
  • _read(size) → emit min(leftBytes, size, 512) zeros → decrement leftBytes → EOF when 0

Mutex:
  • lock(key): check keys map → LOCKED→immediate, UNLOCKED→register callback→wait
  • unlock(key): remove from keys → emit event via setImmediate → callback re-enters lock()

ASYNC/CONCURRENCY PATTERNS
---------------------------
OperationQueue:          Semaphore-based FIFO queue; configurable max concurrency
FSExtentStore:           Two queues (append, read) with different concurrency limits
MemoryExtentStore:       Shared RwLock for in-memory chunks; atomic size tracking
LokiExtentMetadataStore: Arc<Mutex<HashMap>> for metadata; callback-based persistence
Mutex:                   oneshot channels for FIFO waiter signaling

HIGHEST-RISK AREAS
-------------------
1. FSExtentStore (2.3) - largest, hottest path
   • File descriptor lifecycle management
   • Stream piping + explicit sync coordination
   • Pool resource allocation and selection
   • Error handling with state cleanup

2. OperationQueue (2.1) - foundational, heavily used
   • EventEmitter semantics → tokio equivalent
   • Lazy callback execution preservation
   • Concurrency limit enforcement fairness

3. LokiExtentMetadataStore (2.4) - complex pagination
   • Loki replacement (sled vs rocksdb vs in-memory)
   • Pagination state machine correctness
   • Query filter chain (id + time + marker)
